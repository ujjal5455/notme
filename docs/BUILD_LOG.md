## 2026-10-21 · Phase 3 — Database schema, RLS and functions `[pre-event]`

**SQL files created**
| File | Contents |
|---|---|
| `supabase/migrations/0001_tables.sql` | `profiles`, `family_links`, `pairing_codes`, `money_requests` + check constraints, foreign keys, indexes; `pgcrypto` |
| `supabase/migrations/0002_rls.sql` | RLS enabled on all 4 tables; all table rights revoked from `anon`/`authenticated`, then SELECT only re-granted to `authenticated`; 5 SELECT policies; no write policies |
| `supabase/migrations/0003_functions.sql` | `create_my_profile`, `create_pairing_code`, `redeem_pairing_code`, `create_money_request`, `respond_to_request` (all `security definer`, `search_path = ''`, EXECUTE only for `authenticated`) |
| `supabase/checks/rls_checks.sql` | 36 PASS/FAIL security checks with 4 throwaway users; cleans up after itself |

**Key security decisions** (explained in `docs/LEARNING_GUIDE.md`, Phase 3)
- Browser gets read-only access, filtered by RLS; every write goes through one narrow function that checks `auth.uid()` and role.
- `family_id` of a request is copied server-side from `family_links`; the browser cannot choose who receives a request.
- Approve/reject = one conditional `UPDATE … WHERE family_id = auth.uid() AND status = 'pending' AND expires_at > now()`: blocks strangers, the elder, duplicates, late answers and reverting; only `status` and `responded_at` change.
- Timestamps come from the database clock; requested timeout clamped to 15–600 s.
- One trusted family member per elder (`UNIQUE (elder_id)`); single-use 10-minute pairing codes from `gen_random_bytes`.

**Bug found while reviewing and fixed:** `pairing_codes.used_by … on delete set null` would have violated the "used_at and used_by together" check and blocked deleting a family account → changed to `on delete cascade`.

**Bugs found during this phase**
1. supabase-js 2.118.0's `RealtimeClient.channel()` returns an existing channel when the name matches (checked in `node_modules/@supabase/realtime-js/dist/main/RealtimeClient.js`). With React StrictMode's start-stop-start of effects this would reuse a closing channel. Fixed with a counter in the channel name.
2. First draft: if the catch-up check failed while the channel was live, status stayed `offline` forever (nothing polled again). Caught by a new test; fixed by polling after any failed check until one succeeds.
3. A test of mine was wrong, not the code: it checked for `offline` at one moment, but with the 20 ms test poll interval that state lasts only 20 ms. Fixed by recording every status the hook passes through.

- Installed `@capacitor/app` **8.1.2** (MIT, Capacitor's official App plugin). Docs read: capacitorjs.com/docs/apis/app ("Listening for this event will disable the default back button behaviour"; `minimizeApp()` is Android-only).
- New `src/hooks/useBackButton.ts`: on Android only (`Capacitor.isNativePlatform()`), registers one `backButton` listener that calls the newest `onBack` (kept in a ref); if `onBack` returns false, `App.minimizeApp()`. The listener is removed on unmount, so the sign-in screen keeps Android's normal Back.
- `src/SignedInApp.tsx`: Back from any screen goes to the person's home screen (`elderHome` / `familyInbox`); Back on the home screen minimises the app.
- New `src/hooks/useBackButton.test.tsx` (5 tests, plugin faked): handled → no minimise; home → minimise; newest handler used; listener removed on unmount; nothing registered in a browser.
